# 创建需求与任务：富文本和附件

## 数据与执行契约

两个创建窗口共用 `IntakeEditor`：项目可选，编辑器支持加粗、斜体、列表和文件、图片、录音上传。标题取首行；仅附件时取首个文件名。内容序列化为 Markdown，沿用 `goal` / 需求 `description`，不持久化或渲染粘贴的 HTML。其他设置和自动调度行为沿用原有契约：无项目需求仅保存，无项目任务仍可创建 Codex 会话。

沿用 `/api/visual-artifacts` 和 `visual_references` 契约，新增上传参数 `kind: "attachment"`。图片仍按文件签名识别并存储在 `artifacts/visuals`；其他文件按不透明字节存储在 `artifacts/attachments`。附件最多 8 个，每个 10 MiB，文件名去除路径，存储名使用 SHA-256 和受限扩展名。服务器不执行附件，也不把附件作为 HTML 直接提供给浏览器。旧调用不传 `kind` 时保持只接受图片的契约。

需求拆解生成的任务继承同一组托管引用。执行端验证 SHA-256，将远程附件下载到运行目录并重写提示里的路径。只有图片进入 Codex 图片输入；文件和录音通过本地路径供工具读取。附件继续使用原有引用计数式释放逻辑，在最后关联任务结束后清理。云端租户继续拒绝上传服务器文件路径，读写限定在该租户数据目录。

录音上传、存储、播放和执行端文件交付已实现；语音转写由执行环境可用工具完成。提示明确要求无法读取或转写时报告阻塞，不能假定已理解录音。

## 恢复

无新增生产依赖或数据库迁移。若需回退，先暂停调度并停止涉及新附件的活动运行，保留数据库及 `artifacts/attachments`，再整体恢复前后端版本。旧版只识别图片，不能消费新文件引用；恢复调度前须恢复支持附件的版本。不能只回退服务器而继续让旧执行器领取带新附件的任务。
