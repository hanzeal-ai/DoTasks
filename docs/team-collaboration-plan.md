# DoTasks 团队协作方案

日期：2026-09-24。状态：流程与实施契约；本文描述目标行为，不代表运行中的服务已具备这些能力。

## 1. 产品流程

1. 产品 A 上传需求，云端保存原文与附件，向 A 的本地 Agent 投递需求分析运行。
2. A 的本地 Codex 输出风险、待决策问题和模块拆分建议。A 回答问题并确认需求版本、模块边界、验收标准及开发协调人，正式提交需求。
3. 云端按团队、项目权限、模块能力和可承接容量生成候选负责人，Laya 对候选人提供推荐。首版由 A 或有分配权限的协调人确认，确认后才正式派发。
4. B 在云端收到站内通知。B 已预授权自动分析且本地 Agent 可用时，云端触发 B 的本地 Codex 分析任务；离线时保留待领取任务。
5. B 查看分析，选择确认承接、向 A 提问、退回补充、请求改派或报告依赖阻塞。补充内容必须回写需求记录，不能仅留在聊天中。
6. B 确认具体任务版本后才允许开发。代码定位、文件级执行契约及实现计划在 B 侧完成，产品只负责模块级拆分。
7. 开发、验证和代码审查沿用现有执行链路；B 确认交付，协调人确认整体集成结果，A 确认需求验收，需求完成。

首版默认采用人工确认派发，不实现无人确认自动分配。站内通知属于 DoTasks 产品能力，不默认增加邮件、Slack 等外部通知。

## 2. 角色与决策边界

| 参与者 | 负责 | 必须由其他角色完成的决策 |
| --- | --- | --- |
| 产品 A | 需求目标、范围、问题回答、需求提交、最终验收 | 不替 B 确认执行版本，不替审查者通过代码审查 |
| 开发 B | 承接确认、技术分析、开发、验证、交付确认 | 不自行改变产品需求边界，不自动批准需求验收 |
| 开发协调人 | 模块接口、依赖、改派、跨模块集成 | 不替 A 决定产品边界 |
| 云端 | 身份授权、版本、状态转换、任务归属、事件和投递 | 不依赖模型输出跳过硬性门禁 |
| 本地 Agent / Codex | 在对应用户设备上执行获授权的分析或开发运行 | 不代替用户提交、派发、确认开发或验收 |
| Laya | 对已合格候选人给出适配建议 | 不创建候选权限，不直接写状态，不自行启动开发 |

角色可由同一人兼任，但每次操作仍需满足该动作的权限。独立代码审查继续遵守现有审查要求。创建团队的账号为初始团队管理员；管理员管理成员及项目权限，首版允许按已注册账号添加成员，不建设额外邀请、组织架构或排班系统。

## 3. 仓库现状与差距

以下为本次从源文件观察到的行为，未据此声明线上已部署：

| 位置 | 当前行为 | 适配要求 |
| --- | --- | --- |
| `taskboard/cloud/accounts.py`、`tenant_server.py` | 账号认证；每个账号有独立 service/database/vault | 增加显式团队成员、项目权限与团队运行时；保留个人数据隔离 |

| `core/workflow.py`、`core/service/execution.py` | 开发、审查、完成等确定性执行状态和门禁 | 增加团队人工确认门禁，保留已有验证和审查约束 |
| `taskboard/cloud/store.py`、`taskboard/agent.py` | 持久化命令、WSS 唤醒、离线重连；超时命令可以重新领取 | 增加业务运行幂等、准确目标账号及过期租约拒绝，不把消息送达当作任务完成 |
| `taskboard/app_server.py` | 当前 worker 权限用于自主执行，默认具有完整访问能力 | 分析运行需单独的只读执行权限与工具白名单；仅提示词“不要修改”不够 |
| `services/laya-dotasks-decision/decision_service/` | 目前只有历史排序与失败分类接口 | 新增负责人推荐契约及测试，不能宣称现有接口已会分配人员 |
| `web/src/App.jsx`、`taskboard-app.js` | 需求、任务、日志、Token 看板 | 增加团队范围、问题处理、派发、承接确认、交付验收及站内通知 |

账号与 CLI 文件目前有其他未提交改动。本方案不重写这些文件；实现时需基于当时的实际接口适配，不能用本文中的观察覆盖后续修改。

## 4. 单一业务状态来源

团队内每个需求、模块任务和执行运行仅保留一份权威记录，放在团队范围的云端运行时中。个人数据库不复制一套可独立修改的团队任务。

- 账号库负责账号与成员身份；团队运行时负责团队需求、任务、运行、版本、问题和事件。
- 团队范围由已认证身份及有效成员关系解析，服务端逐次检查项目权限。请求中的 `team_id` 仅用于选择资源，不能提供授权。
- 个人工作区继续使用现有隔离运行时。现存个人任务不自动变为团队可见，不自动迁移真实数据库。
- 团队执行继续使用现有 `tasks`、`task_runs`、依赖关系及审查门禁。面向团队的状态展示从权威记录派生，不能在个人数据库或 Laya 中维护另一份执行状态。
- 人员归属使用独立的 `owner_account_id`。现有 `assigned_to` / `claimed_by` 表达 worker 领取，不作为人员权限依据。
- 云端项目使用稳定项目标识，并记录仓库来源身份、允许的基线或来源版本；每位成员在本地确认其项目目录映射。同一仓库在 A、B 设备上路径不同，不传递 A 的绝对路径作为 B 的执行目录。每次运行校验映射与已确认的仓库身份及基线，分析、开发、回调与交付均绑定该身份；同名目录不能作为项目相同的证据。非 Git 项目使用明确登记的项目身份与产物基线。
- 附件、事件流、分析结果、错误、工具调用及下载接口执行同样的团队和项目检查；不能只在列表页过滤。

## 5. 状态与门禁

需求生命周期由需求领域负责，任务生命周期由任务领域负责，投递与运行状态由运行领域负责。页面合成展示，禁止将三个维度混成一个枚举或相互代写。

### 需求

`draft → analyzing → awaiting_product_confirmation → submitted → in_delivery → awaiting_acceptance → done`

- 上传成功只表示已持久化；分析未开始时展示“等待本地分析”。
- 分析失败、预算耗尽或设备不可用时展示对应运行状态，需求仍可补充或重试。
- `submitted` 必须有 A 确认的版本、模块任务、验收标准和协调人。
- 所有模块交付通过且整体集成证据有效，才能进入 `awaiting_acceptance`。
- A 可以验收通过，或明确指出未通过项并创建对应返工，不能用整单模糊驳回覆盖已交付记录。

### 模块任务

`draft → awaiting_assignment → assigned → awaiting_owner_confirmation → ready → 开发/审查 → awaiting_delivery_confirmation → done`

`assigned` 阶段可展示“等待 B 本地接收 / 正在分析”；这些由分析运行派生。`ready` 表示 B 已确认任务版本且执行契约准备完成，依赖尚未满足时仍不得领取开发。

必须有三类独立处理动作：

| 动作 | 进入状态 | 处理人 | 恢复条件 |
| --- | --- | --- | --- |
| 向 A 提问或退回补充 | `awaiting_clarification` | A | 回答落档；有范围变更时发布新版本；B 再确认。默认保留 B |
| 请求改派 | `awaiting_reassignment` | A / 有权限的协调人 | 新负责人通过资格检查，旧运行停止领取，新负责人完成分析和确认 |
| 报告技术依赖阻塞 | `blocked` + 结构化原因 | 协调人 / 依赖负责人 | 依赖满足或明确的解决方案已确认；不自动退回产品 |

开发前提问只阻止启动。开发中发生问题时保留运行证据并暂停受影响部分。暂停、取消、返工继续复用执行领域的行为，新增阶段必须同步进入统一状态转换契约，禁止通过随意更新字符串绕过校验。

## 6. 模块任务与需求版本

A 提交的每个模块至少包括：稳定模块键、标题、目标、范围、不包含内容、可观察的验收标准、对外接口/数据约定、依赖模块。接口或依赖为空时明确记录“无”，不能用遗漏表示已经分析。

产品阶段不要求文件路径、函数名、代码定位证据。B 的分析阶段才准备这些执行信息，复用现有 intake 验证与代码审查规则。

团队模式必须在云端权威 API/MCP 层统一保护现有直达入口，包括 `finalize_task_intake(intake_kind="task")`、ready 状态转换、`auto_dispatch`、直接领取和运行创建。即使调用方提供完整代码定位/执行契约，未提交的团队需求或未经 B 确认的任务版本也不能创建可执行任务或启动开发。入口校验团队需求阶段、认证身份、来源版本和确认记录，不信任客户端宣称“已确认”；个人模式保留既有行为。

- 提交后的需求版本不可原地覆盖，保存原文、结构化模块快照、确认人及时间。
- 模块任务维护自己的修订号，并关联来源需求版本。每个运行绑定明确的任务修订号与执行契约快照。
- 问题记录提问人、回答人、所属模块、来源版本、是否阻塞及关闭结论。普通解释不必增版；改变范围、接口或验收标准必须增版。
- A 与协调人明确受影响模块，按依赖关系扩展影响范围；范围不明时先阻止相关开发，不让模型独自决定“无影响”。
- 发布变更与失效受影响任务的确认在同一事务中完成。受影响任务的旧运行不能提交当前版本交付；未受影响任务维持有效版本和确认。
- 云端停止领取并请求本地中断；无法确认本地已停止时展示“等待停止确认”。本地可能已写出的改动保留在隔离工作区，云端拒绝过期交付不等于撤回本地文件修改。
- 改派、重新启动或发布影响集成的新版本后，旧集成验收失效。不能用旧版本测试证据完成新版本需求。

## 7. Laya 负责人推荐

新增目标接口：`POST /v1/assignment/recommend`。这不是已有接口。

云端先过滤有效团队成员、项目授权、开发角色、模块能力及可承接容量，再将候选账号 ID 和完成推荐所需的最少信息交给 Laya。成员是否在线仅影响执行时间，不自动剥夺其候选资格。

输入包含任务版本、模块目标/边界摘要、候选集及其版本、候选人的相关能力与当前承接情况。个人密码、Agent token、本地文件和无关私有任务不进入输入。

输出包含原候选集内的适配排序、分数语义、模型/策略版本与请求 ID，始终 `advisory_only=true`。分数表示适配等级，不能宣传为成功概率。展示的理由优先引用能力与负载事实，不把未经验证的模型解释当作人员事实。

- 候选集为空：等待人工处理，不从团队外补人。
- 模型不可用、超时、上下文过长或输出无效：保留合格候选列表供人选择，不默认派给第一人。
- 输出新增/遗漏/重复 ID：整份推荐拒绝；不修补成有效分配。
- 超过模型输入上限：明确返回无法推荐；首版不静默截断候选或需求，不比较不同批次未经校准的分数。
- 人工确认时重新验证当前版本、候选资格与容量，使用乐观并发控制；过期推荐不能直接落库。
- 正式分配由云端事务写入归属、通知和待投递事件。Laya 没有这些写权限。

当前历史排序/失败分类的小样本验证不能证明负责人推荐有效。新任务需单独评测；首版人工确认不因评测通过而自动取消。

## 8. 自动分析与可靠投递

复用现有云端队列、WSS 和本地 executor。消息提醒不是唯一事实来源，Agent 连接/重连时从持久化待运行记录恢复。

- 成员为具体团队/项目开启“自动分析”，并设置分析预算与并发限制；默认不开启跨项目分析权限。
- 没有预授权时通知仍可送达，运行保持待确认，由成员主动开始分析。
- 分析运行通过执行器/操作系统沙箱或等效的文件系统权限强制只读项目；普通隔离 worktree 本身不等于只读。拒绝写文件及具有开发写入能力的工具调用；生命周期工具仅允许读取必要上下文、提交分析和问题、续租。确认/派发接口还需独立的服务端身份与动作权限校验。不能沿用开发 worker 的完整访问权限；平台无法提供相应强制约束时禁止自动分析，不能静默降级为仅靠提示词。
- 身份来自认证 token；回调同时检查账号、团队/项目权限、目标运行、租约、任务版本及派发代次，不能信任 payload 的 `worker_id`。
- 每次分析有唯一运行 ID。业务命令以运行 ID 和动作作为幂等键，任务状态与 outbox 同事务提交；outbox 可重放至目标账号队列。
- 本地持久化“准备创建 / 已绑定会话 / 已提交结果”的收据。网络重试复用已绑定会话，不重新建会话。
- 创建会话成功但收据未落盘属于不确定窗口：先核对已有会话；无法确定时标记需处理，禁止仅因超时再次创建。不能宣称跨云端与本地事务具有天然 exactly-once。
- 队列领取、消息已读、Agent 收到、分析完成、B 确认承接是五个不同事实。
- 自动分析预算不等于开发授权；B 明确确认具体版本后，才进入执行契约准备与开发门禁。

## 9. 交付闭环

模块任务交付必须关联执行运行、交付版本、验证结果及所需审查结论，由 B 确认交付。代码任务绑定 Git revision；非代码任务绑定可核验的产物版本/摘要，继续按现有质量门禁决定是否需要代码审查，不强制制造 Git 提交。模型说“完成”或线程结束不能替代这些条件。

协调人对共享接口与整体集成负责。使用独立分支/工作区隔离并行任务；集成记录绑定组成该版本的所有模块交付 revision 及集成目标 revision，验证必须对应这一组合。

当且仅当所有模块已交付、无未解决的阻塞/范围问题、集成结果通过、证据版本一致，需求才允许 A 验收。A 确认后 DoTasks 生命周期结束，不默认延伸到上线部署、运营或长期监控。

如验收不通过，只对明确的缺陷/未满足验收项建立返工，保留此前版本和交付记录。取消与删除不等同于完成，不用于绕过验收。

## 10. 实施顺序与验收

各阶段共同构成最终交付；完成单一后端模块不能宣称团队流程已完成。

| 阶段 | 主要修改边界 | 最小验收 |
| --- | --- | --- |
| 1. 团队与权限 | 账号成员关系、团队运行时、项目标识与本地映射 | A/B 可访问授权团队，C 通过直接 API、附件和事件流均不可越权；个人数据不泄露 |
| 2. 需求与模块 | 数据迁移、需求领域、统一状态机、MCP 契约、需求页面 | A 上传→分析→回答→确认→仅模块拆分→提交；不能提前产生可执行任务 |
| 3. 推荐与派发 | Laya 新接口、DecisionClient、资格过滤、分配动作与通知 | 只推荐合格人员；人工确认生效；过期版本/容量变化/模型异常不误派 |
| 4. 承接与开发 | 分析权限、Agent/executor、回调鉴权、版本门禁、问题页面 | B 离线恢复仅一个有效分析运行；拒绝旧租约和旧版本；B 确认前不能开发 |
| 5. 补充与改派 | 版本、问题、影响范围、运行中断和任务归属 | 补充默认回到 B；改派给新负责人；依赖阻塞不混入产品退回；旧运行不能交付 |
| 6. 交付与验收 | 执行/审查门禁、集成记录、B/A 确认页面 | 错误 revision、缺失验证、未完成子任务阻止完成；完整流程成功结束 |

必要的负向和恢复验证：

1. 两人同时分配、重复点击提交、重复回调、重放过期租约，不产生重复任务或重复开发运行。
2. 非成员、已移除成员、无项目权限的成员及伪造 actor 均不能读写目标资源；跨账号相同局部任务 ID 不串数据。
3. B 离线、服务重启、WSS 丢消息、会话创建结果不确定时可恢复或明确进入待处理状态。
4. Laya 超时、无候选、越界 ID、超限输入时仍可人工派发，且不越过候选硬约束。
5. 分析 worker 通过 shell/文件接口写项目、调用开发工具、调用确认/派发接口时，分别被文件系统/执行器权限和服务端动作权限拒绝；无法建立只读边界时不启动。
6. 开发中变更需求或改派后，旧运行、旧确认、旧集成证据不能完成新任务版本。
